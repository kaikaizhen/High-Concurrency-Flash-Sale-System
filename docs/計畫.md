# High-Concurrency Flash Sale System 實作計畫

> 目標：以 ASP.NET Core Web API 為主體，從一般 CRUD 系統開始，逐步製造並解決高併發問題。
>
> 學習原則：**先看到問題，再導入技術解決問題。**
>
> Git 原則：本專案先只使用 **本地 Git**，不建立 GitHub Repository、不設定 remote、不執行 push。
>
> **【2026-08-28 更新】** 上述「純本地」原則已於 Stage 5 完成後解除。
> 專案已接上遠端並推送：
> <https://github.com/kaikaizhen/High-Concurrency-Flash-Sale-System>
> 下方 §4.1「不設定 GitHub Remote」為當時的決策紀錄，保留以呈現演進過程。

---

## 1. 專案目標

本專案不是單純完成一個「搶購 API」，而是透過版本演進理解高併發系統的核心問題：

1. 一般 CRUD 在高併發下會發生什麼問題？
2. Race Condition 是如何產生的？
3. 如何避免超賣？
4. Transaction、Atomic Update、Optimistic Concurrency 各自解決什麼問題？
5. Redis 為什麼可以降低資料庫壓力？
6. Message Queue 為什麼可以削峰填谷？
7. 如何避免 Request 重送造成重複訂單？
8. Rate Limit 如何保護系統？
9. 多個 API Instance 下，為什麼程式必須 Stateless？
10. 如何透過壓力測試與 Observability 找出瓶頸？


# 7. Stage 2 — Race Condition

## Branch

```text
feature/race-condition
```

---

## 學習目標

不是立刻修問題，而是 **證明 Race Condition 確實存在**。

---

## 情境

設定：

```text
Stock = 100
```

同時送出：

```text
1000 concurrent requests
```

觀察：

```text
成功 Request 數量
Order 數量
Stock 最終值
```

可能產生：

```text
Stock = 0

但是：

Orders = 120
```

或其他不一致結果。

---

## 要理解

```text
Request A
Read Stock = 1

Request B
Read Stock = 1

A Update
B Update
```

單一 Request 沒錯。

問題發生在：

```text
Read → Modify → Write
```

不是 Atomic Operation。

---

## 工具

此階段開始導入：

```text
k6
```

先寫最基本的 load test。

測試：

```text

100 users
500 users
1000 users
```

```text

```

紀錄：

```text

Concurrent Users
Requests
Success
Failure
Orders
Stock After
Observed Problem
```

# 21. 最終學習成果

完成專案後，應該不是只會說：

```text
我會 Redis
我會 RabbitMQ
我會 Docker
```

而是能回答：

```text
為什麼這裡需要 Redis？

為什麼這裡不能只使用 Transaction？

為什麼這個流程需要 Queue？

為什麼 API 必須 Stateless？

為什麼 P95 很低但 P99 很高？

為什麼 Connection Pool 會耗盡？

為什麼 Retry 會產生 Duplicate Order？

Rate Limit 應該放在哪一層？

這個 Bottleneck 是 CPU、Database、Network 還是 Lock Contention？
```

這才是本專案真正要練習的：

> **High-Concurrency System Engineering，而不是單純學會幾個高併發工具。**
