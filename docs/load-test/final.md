> Branch：`feature/load-test`

---

## 1. 一句話結論

**瓶頸是 `Products` 資料表上那一列的排他鎖。**

證據不是推論，是這一組數字：

| | read（有快取） | purchase | 倍數 |
|---|---:|---:|---:|
| RPS | 31,151 | 187 | **167×** |
| P99 | 204 ms | 16,116 ms | **79×** |
| 錯誤率 | 0% | 36.8% | — |
| **峰值 CPU** | **42.8%** | **2.4%** | **1/18** |

同一台機器、同一個行程、同一個壓測工具。
**慢 167 倍的那一條路徑，CPU 用得少 18 倍。**

系統不是「忙不過來」，是「在等」。

---

## 2. 排除法

計畫 §15 要求回答「這個 Bottleneck 是 CPU、Database、Network 還是 Lock Contention」。
逐項排除：

| 候選 | 證據 | 判定 |
|---|---|---|
| **CPU** | 搶購飽和時 CPU 只有 2.4%；讀取跑到 31k RPS 也才 42.8% | ❌ 不是 |
| **記憶體** | 峰值 704 MB，沒有 GC 壓力徵兆，執行緒數穩定在 36–59 | ❌ 不是 |
| **執行緒池** | 執行緒數沒有暴增（若同步阻塞吃光執行緒池會看到緩慢爬升） | ❌ 不是 |
| **Redis** | 全程延遲 0.4–31 ms，讀取路徑 99.5% 命中 | ❌ 不是 |
| **網路 / 頻寬** | 讀取路徑同樣走網路卻能跑 31k RPS | ❌ 不是 |
| **資料庫整體負載** | 讀取路徑 327 萬請求只用了 63 次 DB 命令 | ❌ 不是 |
| **單一資料列的鎖競爭** | 見下 | ✅ **是** |

### 決定性證據

`stress / purchase` 時**診斷端點自己的查詢**花了 4,497 ms，
而且有 11 次取樣完全逾時。

那個查詢是 `SELECT HAS_PERMS_BY_NAME(...)` —— 它**不碰 Products 表**。
它變慢代表整個資料庫連線層已經被搶購請求塞滿：
5000 個 VU 各自持有一條連線、在同一列上排隊，
連一個無關的輕量查詢都擠不進去。

這正是 Stage 3 量到的現象在更大規模下的重演。

## 3. 為什麼是「一列」而不是「一張表」

搶購的核心是這一句：

```sql
UPDATE Products
SET Stock = Stock - @qty
WHERE Id = @productId AND Stock >= @qty
```

秒殺的定義就是「所有人搶同一件商品」。
於是**所有請求都在爭奪同一個 `Id` 的那一列**。

SQL Server 對該列的排他鎖一次只能給一個交易。
不管有幾台 API、幾核 CPU、多快的網路，
這一列的更新永遠是**序列化**的。

單次交易約 5–7 ms（UPDATE + INSERT + commit，跨網路到遠端 SQL Server），
1000 ÷ 6 ≈ **167 次/秒** —— 與實測的 141~187 RPS 吻合。

**這個數字是被單次交易的耗時決定的，不是被系統資源決定的。**

## 4. 各階段的努力，回頭看

| Stage | 做了什麼 | 對這個瓶頸的影響 |
|---|---|---|
| 3 併發控制 | 選定 Atomic Update | 讓它**正確**，沒有變快 |
| 4 Redis | 讀取快取 | 讀取路徑快 167 倍，**寫入路徑毫無改變** |
| 5 Queue | 訂單非同步化 | 資料庫寫入量減半，API 吞吐不變 |
| 7 限流 | 拒絕過量請求 | 保護系統不崩，**不提高容量** |
| 8 多 Instance | 三台 + 負載平衡 | 讀取可水平擴充，**寫入不行** |

**Stage 8 是最值得注意的一項。** 讀取路徑加機器就能線性擴充，
但搶購路徑加到三十台也還是那一列的鎖 ——
所有 Instance 都在跟同一列說話。

> 水平擴充只能擴充「不共享的東西」。

## 5. 如果流量再成長 10 倍，下一步會改什麼

現在約 187 RPS，目標 1,870 RPS。依投資報酬率排序：

### 5.1 庫存扣減移到 Redis（最直接）

把庫存本身放進 Redis，用 Lua 腳本做原子扣減，資料庫只負責最終對帳。

- Redis 單執行緒處理單一 key 的操作約 0.1 ms 量級 → 理論上限提升到數千 RPS
- Stage 8 的 `RedisSlidingWindowRateLimiter` 已經證明這個模式可行
- **代價**：Redis 成為真相來源，必須處理它與資料庫的最終一致性，
  以及 Redis 故障時的降級策略

### 5.2 庫存分桶（Stock Segmentation）

把 100 件庫存拆成 10 個桶各 10 件，請求隨機落到一個桶。
鎖競爭從「1 列」變成「10 列」，理論上 10 倍。

- **代價**：某個桶賣完但其他桶還有貨時，會誤判為售完。
  需要跨桶重試或動態再平衡。

### 5.3 純非同步搶購

連庫存扣減都放進佇列，由單一 Worker 序列處理，API 只回「已受理」。

- 資料庫端完全沒有競爭
- **代價**：使用者無法立即知道有沒有搶到 —— Stage 5 §2 已經論證過
  這是把超賣從資料錯誤變成對客戶的謊言。
  只有在業務上能接受「稍後通知結果」時才成立。

### 5.4 不該做的事

| 做法 | 為什麼沒用 |
|---|---|
| 加 API Instance | CPU 才 2.4%，瓶頸不在 API |
| 升級 API 機器規格 | 同上 |
| 加大連線池 | 更多連線只會在同一列上排更長的隊 |
| 換更快的併發控制演算法 | Stage 3 已證明三種的天花板一樣 |

## 6. 尚未量測到的東西

誠實列出這份報告的邊界。

### 6.1 k6 與 API 共用同一台機器

兩者競爭同樣的 12 核。讀取路徑的 31k RPS 上限**有一部分是 k6 自己造成的**，
真實容量應該更高。

這個數字適合用來比較不同版本，不適合當成絕對容量。
要拿到可信的絕對值，壓測機必須與被測系統分離。

### 6.2 DB 連線數量不到

壓測所用的資料庫帳號沒有 `VIEW SERVER STATE` 權限，
`sys.dm_exec_sessions` 只看得到自己那一條。

第一版程式碼直接回報那個數字（永遠是 1），比不回報更糟 ——
「連線數 1」會讓人以為連線池很閒，實際上可能已經耗盡。
已改為明確回報 `-1`（量不到）。

要啟用：`GRANT VIEW SERVER STATE TO [<db-user>]`

### 6.3 多 Instance 下的壓測

本次全部在單一 Instance（非 Docker）上執行，
以便與 Stage 2–7 的數據直接比較。

Docker Desktop 在 Windows 上的埠轉發約在 100 req/s 就會開始重設連線
（Stage 8 已記錄），因此無法透過 `localhost:8080` 對叢集做高流量壓測。

要量多 Instance 的真實容量，k6 必須跑在容器網路內。

### 6.4 資料庫端的細節

沒有量到 SQL Server 內部的 `wait_stats`、鎖等待時間分布、
或 tempdb 壓力。那些需要 DBA 權限，也超出這個階段的範圍。

目前的結論（「瓶頸是那一列的鎖」）是從應用程式端的行為推論的，
證據充分但不是直接證據。

## 8. P95 / P99 的變化

### 讀取路徑

| VU | RPS | P95 | P99 |
|---:|---:|---:|---:|
| 10 | 7,509 | 2.0 ms | 6.0 ms |
| 100 | 26,570 | 5.1 ms | 10.4 ms |
| 5,000 | 31,151 | 96.9 ms | 204.3 ms |

100 → 5000 VU（50 倍負載），RPS 只多 17%，但 P99 漲了 20 倍。

**這是飽和的典型形狀**：吞吐量到頂之後，多出來的負載全部變成排隊時間。

### 搶購路徑

| VU | RPS | P50 | P99 | 錯誤率 |
|---:|---:|---:|---:|---:|
| 100 | 141 | 629 ms | 930 ms | 0% |
| 5,000 | 187 | **15,002 ms** | 16,116 ms | **36.8%** |

P50 就已經 15 秒 —— 不是少數請求慢，是**一半以上的請求都在等 15 秒**。

36.8% 的失敗是逾時，不是系統回錯：請求排在鎖的佇列裡等到客戶端放棄。

> 這也解釋了為什麼 Stage 7 的限流是必要的：
> 系統在飽和時不會自己拒絕請求，它會讓所有人一起慢慢等到全部逾時。
> 快速拒絕一部分人，剩下的人才有機會被服務。
